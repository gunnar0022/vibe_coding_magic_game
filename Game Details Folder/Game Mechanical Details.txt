MECHANICS AND SYSTEM DESIGN


––––––––––––––––––––
PART 1 — DATA VS OBJECTS 
––––––––––––––––––––

– Spells should primarily be data (JSON, tables, dictionaries)
– World participants must be objects

SPELL EXECUTIONS MAY CREATE TEMPORARY OBJECTS

Meaning:
– A spell definition is static data
– Casting a spell may spawn a transient “effect instance” object

This separation is essential for modularity.

Similarly:
– Items should be objects
– Item definitions should be data

Think in terms of:
DEFINITIONS = data
INSTANCES = objects

––––––––––––––––––––
PART 2 — CORE OBJECT TAXONOMY
––––––––––––––––––––

You only need a small number of base object types. Everything else should be composition.

BASE WORLD OBJECT
This is the root of everything that exists in the world.

Responsibilities:
– Unique ID
– Position (grid or world coordinates)
– Bounding box / hitbox
– Tags (tree, npc, water, flammable, etc.)
– Reference to components

This object does NOT assume:
– Health
– Inventory
– Intelligence
– Magic

Those are added via components.

––––––––––––––––––––

ACTOR (LIVING ENTITY)
Player, NPCs, monsters all fall here.

Required components:
– Stats component (health, stamina, mana, resistances)
– Status component (flags, timed effects, conditions)
– Inventory component (optional)
– Equipment component (optional)
– Interaction component (can talk, attack, react)

Player, NPCs, and enemies differ only by:
– Control source (player input vs AI)
– Dialogue capability
– Behavior trees

This avoids special-casing the player later.

––––––––––––––––––––
INANIMATE OBJECT
––––––––––––––––––––

Trees, rocks, logs, walls, water tiles, ruins.

Possible components:
– Structural integrity (health or durability)
– Resource container (what drops when altered or destroyed)
– Environmental traits (flammable, porous, conductive, brittle)
– State machine (intact, cracked, burning, flooded, dormant)
- Damage type immunities 

Water is not “special” — it is just an object with:
– Infinite or regenerating volume
– Specific reaction rules


––––––––––––––––––––
ITEM INSTANCE
––––––––––––––––––––

Item INSTANCE responsibilities:
– Reference to item definition
– Quantity (if stackable)
– Condition or durability
– Ownership or container reference

Item DEFINITION (data):
– Name
– Weight
– Value
– Tags
– Use effects
– Equipment slot (if any)

This allows:
– Rocks holding loot
– Enemies carrying items
– Trees dropping resources
– Player inventories without hacks

––––––––––––––––––––
PART 3 — MAGIC INTEGRATION (HOW OBJECTS RESPOND)
––––––––––––––––––––

Each world object should expose a single interface, conceptually:

ON_MAGIC_APPLIED(spell_descriptor, context)

The object itself decides:
– Does this affect me?
– Which traits matter?
– What state changes occur?

Spell data contains:
– Category
– Element / physical type
– Interaction traits
– Intensity or magnitude

Objects contain:
– Reaction rules
– Thresholds
– State transitions

Example:
A tree does not know “Fireball.”
It knows:
– fire element could trigger burning state
– immunity to immediate elemental damage
– immunity to many status like poison. 
- susceptible to slashing damage past a certain threshold
-> the fire would trigger a burning effect.


––––––––––––––––––––
PART 4 — EFFECT INSTANCES 
––––––––––––––––––––

When a spell is cast, you should create a temporary EFFECT OBJECT.

Effect instance responsibilities:
– Position and area of influence
– Duration
– Tick/update behavior
– Applies spell descriptor to overlapping objects

This lets you support later:
– Lingering fire
– Expanding water
– Wind zones
– Social influence auras

Without rewriting spells.

––––––––––––––––––––
PART 5 — SKELETON SETUP INSTRUCTIONS
––––––––––––––––––––

Here is a clean, minimal setup order for these systems:

Define BASE WORLD OBJECT
Only position, ID, tags, components

Implement COMPONENT SYSTEM
Stats
Status
Inventory
Environmental traits

Implement ACTOR using components
Player first
Then NPC
Then enemy

Implement INANIMATE OBJECTS
Tree, rock, wall, water
No art, only logic

Implement ITEM DEFINITIONS (data)
Then ITEM INSTANCES (objects)

Implement SPELL DESCRIPTORS (data only)

Implement EFFECT INSTANCE OBJECT
Connect spells to world reactions

At this point:
– The world reacts
– Nothing is hardcoded
– Everything is extensible

––––––––––––––––––––
FINAL GUIDING PRINCIPLES
––––––––––––––––––––

– Objects store state
– Data defines rules
– Spells describe traits, not outcomes
– Objects decide how to change
– Effects mediate interaction

###IMORTANT ELEMENTS ###
––––––––––––––––––––


––––––––––––––––––––
CORE MAGIC CONCEPT
––––––––––––––––––––

Magic is expressed through discrete symbols resembling Chinese or Japanese characters. Each symbol represents a fundamental concept, such as an element, force, or abstract principle.

Symbols are unlocked gradually through exploration, NPC interaction, environmental discovery, or narrative progression.

––––––––––––––––––––
SYMBOL USE
––––––––––––––––––––

Symbols may be cast individually or combined in pairs. Combination order does not matter. Each valid pair is hand-authored and finite, including ineffective or “dud” outcomes.

There is no procedural generation of spell results. All outcomes are authored, but resolved through abstraction.

––––––––––––––––––––
SPELL RESOLUTION PHILOSOPHY
––––––––––––––––––––

Spell combinations do not directly encode effects. Instead, each combination resolves into a set of internal characteristics.

These include:

A high-level category such as Destructive, Environmental, Social, or other future categories
An elemental or physical classification, including non-elemental types
One or more interaction traits such as pressure, slashing, erosion, influence, or similar

SPELLS DO NOT KNOW THEIR TARGETS.
OBJECTS AND ENTITIES KNOW HOW THEY RESPOND.

Trees, water, terrain, structures, creatures, and NPCs define their own reaction logic to incoming spell characteristics. The same spell may produce very different outcomes depending on context.

––––––––––––––––––––
STATIC VS DYNAMIC WORLD INTERACTION
––––––––––––––––––––

The world layout is largely static. Buildings, terrain, towns, rivers, and landmarks are hand-authored and stable.

Dynamic behavior emerges from systems layered on top of this structure:

Environmental reactions to spell traits
Growth, decay, and regeneration
State changes in objects and NPCs
Puzzle resolution through experimentation

––––––––––––––––––––
PLAYER KNOWLEDGE AS PROGRESSION
––––––––––––––––––––

Player understanding is a core mechanic.

During gameplay, the magic interface displays only available symbols as characters. No explanations are shown. The player must rely on memory, intuition, and experience.

The player maintains a magic notebook that acts as a personal journal.

––––––––––––––––––––
PLAYER NOTEBOOK DESIGN
––––––––––––––––––––

The notebook is interactive and optional. It does not directly alter gameplay outcomes.

Each symbol has a game-defined reference page explaining the symbol as a fundamental unit, without listing combinations.

Adjacent to this, the player may create freeform note pages. These pages may contain hypotheses, observations, incorrect conclusions, keywords, or organizational structures defined entirely by the player.

Players may create folders, subfolders, and custom groupings. These can act as personal loadouts, thematic collections, or experimental logs.

When new symbols are discovered, minimal information is auto-recorded, primarily contextual. A symbol learned from an NPC may come with richer explanation. A symbol discovered in the wild may initially be recorded as unknown, with only location or circumstance noted.

Players are explicitly allowed to be wrong. Incorrect notes are valid and expected.

The player will get out of the notebook roughly what they put into it.

The notebook will have to implement input sanitation to prevent any unwanted attacks on the game itself.


––––––––––––––––––––
NPC FUNCTION
––––––––––––––––––––
NPCs act as teachers, informants, and narrative anchors. They unlock symbols, provide partial explanations, and share perspectives, but do not grant mastery.
Knowledge must be internalized and applied by the player.

––––––––––––––––––––
MAGIC FAILURE AND DETERMINISM
––––––––––––––––––––

Magic resolution is fully deterministic. Every symbol or symbol combination resolves consistently to the same underlying characteristics and outcomes. However, determinism does not imply safety or usefulness. Some combinations intentionally produce no effect, while others may generate outcomes that are neutral, situationally harmful, or directly detrimental to the caster. Negative outcomes are not treated as failures of the system, but as valid expressions of magical behavior within the world.

Certain spells may produce effects that harm the caster as well as surrounding entities, such as area-based damage-over-time, environmental decay, or destabilizing status conditions. In addition, the system supports state-driven inhibition, where environmental conditions, entity states, or contextual constraints may prevent a spell from executing at all. This functionality exists to preserve extensibility and does not imply randomness or chance-based failure.

––––––––––––––––––––
MAGIC INTROSPECTION AND DEBUGGING
––––––––––––––––––––

To support player understanding without undermining discovery, the game provides an optional introspection mechanism usable outside of combat. Introspection presents a first-person internal reflection summarizing recent magical actions and their observable outcomes. This serves as an in-world explanation layer rather than a technical debug interface.

Introspection focuses on qualitative observations such as apparent area of effect, duration, affected entities, and visible status conditions. It avoids numerical precision and exact damage values. Statements reflect uncertainty and learning rather than authority, reinforcing the player’s role as an experimenter interpreting results rather than a user reading system output.
