STRUCTURAL IMPLEMENTATION PLANNING

––––––––––––––––––––
CORE TECHNICAL DIRECTION
––––––––––––––––––––

Understand that there is a lot of established lore about the background of this game, but that can only be focused on after most if not all of these structural systems are first established and polished. 

The project should be treated as a systems-driven simulation rather than a content-heavy RPG. A lightweight 2D framework is preferred to keep logic explicit and iteration fast.

Architecture priorities include clarity, determinism, and extensibility.

––––––––––––––––––––
MAGIC SYSTEM IMPLEMENTATION
––––––––––––––––––––

Symbol pairs must be normalized to enforce order independence.

We'll likely rely on a very large number of Boolean status trackers that will get called into play when a new effect is applied to creatures or objects (ex. an object may have a burning status, but when affected by a water condition, it checks the interaction and resolves with removing the burning status) There will be many status to track

Spell definitions resolve into abstract descriptors rather than direct effects.

World objects define reaction logic based on incoming spell traits.

All spell definitions should be hand-authored and stored in structured data formats such as JSON.

––––––––––––––––––––
DATA SEPARATION
––––––––––––––––––––

Static world data must be separate from dynamic state.

Dynamic state includes player progress, unlocked symbols, notebook content, and world object states.

This data must be persistable and reloadable. A lightweight database or structured files are sufficient.

ROUGH DEVELOPMENT ORDERING

––––––––––––––––––––
PHASE 1 — EXECUTABLE FOUNDATION
––––––––––––––––––––
Minimal 2D runtime
Player entity on a grid
Movement and collision
Basic input handling
Camera or viewport if needed

Placeholder world objects
Simple tiles or entities with IDs
Dummy objects with obvious properties (tree, rock, water, wall)
No art polish, only semantic clarity

The goal of Phase 1 is “something moves and something exists.”

––––––––––––––––––––
PHASE 2 — MAGIC AS DATA, NOT EFFECT
––––––––––––––––––––

Symbol registry
Define symbols as data entries only
No UI yet, no visuals beyond identifiers

Core magic resolution logic
Symbol normalization
Pair lookup
Resolution into abstract spell descriptors
No effects yet

Minimal object reaction interface
Objects expose a simple reaction function
Input: spell descriptors
Output: log or state change

At the end of Phase 2, you should be able to cast a symbol pair and see a deterministic response in logs or simple state flags.

––––––––––––––––––––
PHASE 3 — PLAYER KNOWLEDGE LOOP
––––––––––––––––––––

Magic casting interface (minimal)
Select symbols
Cast spell
No explanations

Notebook system (foundational)
Auto-record symbol discovery
Store context of discovery
No freeform notes yet

This validates the “memory over UI” premise early, before content grows.

––––––––––––––––––––
PHASE 4 — WORLD CONTEXT
––––––––––––––––––––

Small static test map
One or two screens
Designed specifically to test interactions

Environmental reaction rules
Trees reacting to traits
Water reacting differently
Terrain states changing

Iterative refinement pass
Tighten spell descriptors
Adjust object reactions
Cull redundant or unclear interactions

This phase is where the game starts to feel real.

––––––––––––––––––––
PHASE 5 — LEARNING AND EXPANSION
––––––––––––––––––––

NPC teachers
Symbol unlocking
Partial explanations
Conflicting interpretations

Notebook expansion
Freeform note pages
Folders and player organization
Keywords and search

Content scaling (still small)
More symbols
More objects
More interaction density

––––––––––––––––––––
PHASE 6 — DEFERRED SYSTEMS
––––––––––––––––––––

Combat

Advanced AI

Large maps

Long-term progression systems

––––––––––––––––––––
NON-GOALS AND AGENT FREEDOM
––––––––––––––––––––

The system permits broad exploration, iteration, and autonomous expansion during development. No hard prohibitions are imposed on systemic experimentation, with the understanding that outcomes may be refined, constrained, or re-authored manually as clarity improves. Agent-driven development is encouraged to explore possibilities first, with human curation applied afterward to preserve thematic and mechanical coherence.

KEY RISKS

Hardcoding spell-to-object behavior
Undermining memory-based design with UI shortcuts
Expanding scope before system clarity is achieved

––––––––––––––––––––
MINIMUM VERTICAL SLICE
––––––––––––––––––––

Initial development should target a minimal but complete experience slice. This includes a single small map, a limited set of symbols, a handful of reactive objects, one NPC teacher, and at least one interaction or puzzle that can only be resolved through correct symbolic understanding. This slice must demonstrate the full knowledge loop: discovery, experimentation, consequence, and learning.
